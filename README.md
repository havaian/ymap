# Y.Map

Гражданская платформа мониторинга и прозрачности инфраструктуры для Узбекистана. Жители сообщают о фактическом состоянии социальных объектов, аналитика и программы видны публично, а органы управления получают срез реальной картины (Стратегия «Узбекистан - 2030»).

Прод: `ymap.ytech.space`
Репозиторий: `https://gitlab.ytech.space/others/ymap.git`

## Стек

- Фронтенд: Nuxt 4 (Vue 3, Pinia, @nuxtjs/i18n RU/UZ, Tailwind, Leaflet), SSR через Nitro node-server. Каталог `frontend/`.
- Бэкенд: Node.js (ESM) + Express, MongoDB (Mongoose), Redis. Каталог `backend/`.
- Бот: Grammy (Telegram). Каталог `bot/`.
- Инфраструктура: Docker Compose + Nginx.
- ИИ: Google Gemini (анализ обращений на стороне бэка).

## Структура репозитория

```
ymap/
  backend/         # Express API (MongoDB, Redis, JWT)
  bot/             # Telegram-бот (Grammy)
  frontend/        # фронт на Nuxt 4 (SSR, Nitro node-server)
  docker-compose.yml
  .env.sample
```

Фронт мигрирован с React 19 + Vite на Nuxt 4. Старый React убран, `frontend/` теперь Nuxt.

## Требования

- Node.js 20+ и npm.
- MongoDB и Redis (либо через Docker).
- Docker + Docker Compose - для контейнерного запуска.

## Быстрый старт (Docker Compose)

1. Скопируйте пример окружения:

```
cp .env.sample .env
```

2. Заполните переменные (см. раздел «Переменные окружения»): как минимум `MONGODB_URI`, `REDIS_URL`, `JWT_SECRET`, `TELEGRAM_BOT_TOKEN`, `GEMINI_API_KEY`, `BOT_EMAIL`, `BOT_PASSWORD`.

3. Поднимите сервисы:

```
docker compose up -d --build
```

Сервисы: `frontend` (Nuxt SSR, порт 3000), `backend` (порт 4000), `bot`, `redis` (порт 7791).

Маршрутизация: сервис `frontend` собирается из `./frontend/Dockerfile` (multi-stage: сборка Nuxt, затем запуск `node .output/server/index.mjs`) и слушает порт 3000. Запросы `/` на фронт и `/api` на бэкенд разводит внешний host-nginx (как и в версии на React). В SSR Nuxt ходит на бэкенд напрямую через `NUXT_INTERNAL_API_BASE`, на клиенте - через `NUXT_PUBLIC_API_BASE` (по умолчанию `/api`).

## Локальная разработка

Бэкенд:

```
cd backend
npm install
npm run dev        # nodemon, порт из BACKEND_PORT (по умолчанию 4000)
npm run seed       # опционально: наполнение БД
```

Фронтенд (Nuxt):

```
cd frontend
npm install
npm run dev        # http://localhost:3000
```

`NUXT_PUBLIC_API_BASE` по умолчанию `/api` (один origin за Nginx). При отдельном запуске задайте базовый URL бэка либо проксируйте `/api` на Express.

Проверки Nuxt:

```
npm run typecheck
npm run build
```

## Композитный индекс и карточка объекта

`GET /api/analytics/composite` - районный композит по реестрам объектов.

- Нормализация **по рангам**, не min-max: один район с невозможной загруженностью
  иначе прижимает все остальные ко дну диапазона, и ошибка в данных становится
  единицей измерения.
- Веса объявляются. По умолчанию равные, переопределяются как `?w.deprivation=2`
  и так далее, ответ всегда несёт использованные веса.
- Компонент без значения не считается нулём: его вес перераспределяется.
- Анализ чувствительности: 1000 прогонов, веса возмущаются до ±50 %, в ответе
  доля прогонов, в которых район остаётся в верхней полосе. Генератор
  детерминированный и засеян из запроса, поэтому два одинаковых вызова дают
  одинаковые числа. Меняется через `?seed=`.
- Итоговое число никогда не возвращается без разложения: у каждого района лежат
  значение, ранг, вес и вклад по каждому из четырёх компонентов плюс знаменатели.
- Обращения, голоса и проверки в композит **не входят**: гражданский контур пуст,
  и район получал бы хорошую позицию за отсутствие пользователей.

`GET /api/objects/:id/profile` - карточка объекта, страница `/objects/:id`,
открывается кликом по маркеру на карте.

Показывает разложение депривации по измерениям с исходным значением реестра рядом
с каждым вердиктом, показания мощности и возраста, отметки качества записи и
историю из архива. Каждое изменение несёт окно между снимками, а не точку во
времени. Пустое поле показывается как пустое, а не как ноль.

## Скрипты границ

Порядок и что делает каждый. Все читают `backend/src/data/`, пишут только те,
где это сказано.

**Состояние на 08.08.2026.** Границы перезалиты из OSM и прошли аудит чисто:
14 регионов из 14, 189 районов из 198, ноль прямоугольников, медиана вершин 615
у районов и 2565 у регионов. `simplify-boundaries.js` срезал 86,8 % и 84,6 %.

Незакрытое:

- **9 записей кроссволка без границы**: семь городов (Jizzax, Shahrisabz, Termiz,
  Bekobod, Yangiyoʻl, Urganch, Xiva) и два района (Xatirchi, Nurobod). Причина
  выясняется, а не угадывается: `probe-missing-boundaries.js` спрашивает у OSM,
  что для них есть на уровнях 4-9, и раскладывает на три случая - единица есть на
  другом `admin_level`, единица есть под другим именем, единицы нет вовсе. Первый
  случай чинится флагом `--extra-district-levels=`, второй - вариантом имени в
  кроссволке, третий кодом не чинится.
- **44 объекта Хатырчи и Нурабада** остались с `districtId: null`. Это лучше
  прежнего: у них была геометрия-прямоугольник, а отсутствующая граница видна.
- **9 границ OSM без пары в кроссволке.** Восемь - единицы, которых в кроссволке
  нет: он собран из duasr.uz и покрывает только районы с объектами. Девятая,
  `Matbuotchilar ko'chasi`, это улица с тегом `admin_level=6`.

Закрыто в матчере и данных:

- `Nókis qalası hákimiyatı` ↔ `Nukus shahar` - каракалпакское `qala` опознаётся
  как город, `hákimiyatı` отбрасывается.
- `М.Улугбек т.` ↔ `Mirzo Ulugʻbek tumani` - односимвольный инициал принимается
  как префикс, но только в имени из нескольких слов.
- `Бозатау т.` ↔ `Boʻzatov tumani` - каракалпакское словоконечное `-au` и узбекское
  `-ov` сворачиваются к одной форме.
- `1714401 Namangan shahar` держал в именах `Давлатобод т.` - разные единицы в
  одной записи. Найдено проверкой по коду: пятая цифра СОАТО кодирует тип единицы
  (2 - район, 4 - город), правило держится на всех 198 записях, и это имя было
  единственным исключением. Имя перенесено в `nameConflicts`, из сопоставления
  исключено, как наблюдение сохранено. Проверка: `validate-crosswalk.js`.

Регрессия матчера: 198 записей, ноль коллизий, 140 пар латиница/кириллица из 141
сходятся, город и одноимённый район по-прежнему различаются.

**Где что запускается.** Скрипты делятся ровно на две группы, и граница между
ними - нужна ли база.

| Группа | Что нужно | Где запускать |
|---|---|---|
| Скачивание и проверка файлов | Node 18 и сеть | **локально**, в корне репозитория |
| Импорт и аналитика | MongoDB | в контейнере |

У первой группы нет внешних зависимостей - только встроенные модули Node,
`npm install` не требуется. Результат коммитится и приезжает в образ обычным
`COPY` при сборке, поэтому контейнер данные только читает и разделяемых каталогов
между хостом и контейнером нет вовсе. Это снимает целый класс проблем: каталог
`backend/src/data` лежит внутри рабочей копии git, деплой делает
`git reset --hard`, а удаление файла требует прав на каталог - отдать его
контейнеру значит уронить пайплайн на `Permission denied`.

Локально:

```
# Весь локальный конвейер одним прогоном, с отчётом об изменённых файлах
node backend/src/scripts/refresh-data.js            # сборка и проверки
node backend/src/scripts/refresh-data.js --fetch    # вместе со скачиванием
node backend/src/scripts/refresh-data.js --list     # список этапов

# Те же шаги по отдельности
node backend/src/scripts/validate-crosswalk.js
node backend/src/scripts/probe-missing-boundaries.js
node backend/src/scripts/fetch-osm-boundaries.js --debug
git add backend/src/data/osm-regions.geojson backend/src/data/osm-districts.geojson
git commit -m "boundaries: refetch from OSM"
git push
```

В контейнере, после деплоя:

```
docker compose exec backend node src/scripts/import-geodata-osm.js --dry-run
docker compose exec backend node src/scripts/import-geodata-osm.js --prune-stale
docker compose exec backend node src/scripts/import-objects.js
docker compose exec backend node src/scripts/simplify-boundaries.js
docker compose exec backend node src/scripts/audit-geodata.js
```

Если скачивание всё же обязано идти там, где каталог принадлежит не вам,
переменная `GEODATA_DIR` перенаправляет запись, а чтение по-прежнему находит
закоммиченный файл.

Три барьера, которых раньше не было:

- `fetch-osm-boundaries.js` не запишет файл, если геометрия вырождена в bbox.
- `import-geodata-osm.js` не запишет такую геометрию в базу.
- `import-geodata-osm.js` сообщает о документах, которых нет в текущем прогоне.
  Импортёр апсертит и никогда не удаляет, поэтому район, переставший
  сопоставляться, сохраняет документ прошлого прогона навсегда - именно так два
  bbox пережили полный перезалив. Удаление: `--prune-stale`, после него
  **обязательно** `import-objects.js`, иначе часть объектов останется с
  `districtId` в никуда.

| Команда | Пишет | Зачем |
|---|---|---|
| `node src/scripts/audit-geodata.js` | нет | Считает районы по `apiId` до и после миллиона: до - ключ crop.agro, после - ключ OSM relation. Оба набора сразу означают, что районы лежат в базе дважды и хороплет рисует их поверх друг друга |
| `node src/scripts/validate-crosswalk.js` | нет | Сверяет имена в кроссволке с типом единицы по пятой цифре кода СОАТО. `--fix` переносит противоречащие имена в `nameConflicts` |
| `node src/scripts/probe-missing-boundaries.js` | нет | Спрашивает OSM, что есть для записей без границы на уровнях 4-9, и говорит, чинится ли это уровнем, именем или не чинится вовсе |
| `node src/scripts/inspect-boundaries.js` | нет | Отличает настоящий контур от bbox: число вершин плюс отношение площади кольца к площади его bbox |
| `node src/scripts/fetch-osm-boundaries.js` | `data/osm-*.geojson` | Основной источник, Overpass. ODbL, атрибуция обязательна |
| `node src/scripts/fetch-geoboundaries.js` | `data/osm-*.geojson` | Запасной источник, статические файлы. CC-BY 4.0. Имена файлов те же, поэтому скрипт читает источник уже лежащего файла и отказывается перезаписывать чужой без `--overwrite` |
| `node src/scripts/import-geodata-osm.js --dry-run` | нет | Сопоставление границ с СОАТО без записи |
| `node src/scripts/import-geodata-osm.js` | `regions`, `districts` | Загрузка границ |
| `node src/scripts/simplify-boundaries.js` | `geometrySimplified` | Копия под отрисовку. Хороплет и контур региона отдаются из неё, полная геометрия остаётся |


Важно перед деплоем:

- Публичные без логина: `/api/analytics`, `/api/regions`, `/api/districts`, `/api/markers`.
- Отключены: `POST /api/issues` (веб-подача обращений), `POST /api/ai/analyze`, роут `/api/admin`. Отключённое сохранено в коде в виде комментариев (обратимо).
- Отключение `POST /api/issues` и `POST /api/ai/analyze` ломает текущий сценарий Telegram-бота (`/report` -> анализ -> создание обращения). Выкатывать только скоординированно с запуском Doppix.
